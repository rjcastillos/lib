# Specification review: ambiguity, consistency, and gaps

https://chatgpt.com/share/6ad7cb68-5414-83eb-812f-66dcd26b1d32

reviewed study/`README.md` as a technical specification for a financial OHLCV data-processing pipeline that calculates candlestick features, ATR, relative volume, moving averages, slopes, and predecessor-bar relationships, then exports the results to JSON and CSV.

Overall assessment: The specification provides a useful foundation, with concrete formulas and examples, but several areas are underspecified or contradictory enough to produce different results across implementations. 

The highest-risk issues are 

the candlestick classification logic, 

the mapping of predecessor patterns, 

indicator initialization, 

handling of missing or zero values, 

and CSV/JSON output consistency.

I have organized the findings by priority and included a proposed resolution for each. The recommendations below distinguish defects or ambiguities in the current document from design decisions that still need your confirmation.

## 1. Highest-priority findings

P1 — Candle classification

High risk

The neutral-candle rules conflict with the bullish/bearish branches, and some shape rules can overlap. Several neutral, boundary, and degenerate candles have no defined output for every field.

Proposed resolution: establish an explicit classification precedence and define outputs for every candle type.

P1 — Predecessor patterns

High risk

The 12 combinations are mathematically enumerable, but the pattern names and categories are inconsistently mapped. Some labels contradict the underlying high/low relationships.

Proposed resolution: define a complete, canonical 3 × 3 classification table and validate every name against its code.

P1 — Indicator initialization

High risk

ATR, EMA, SMA, and slopes do not share one fully specified warm-up and initialization policy. This can shift outputs between libraries and implementations.

Proposed resolution: specify formulas, seed values, first valid index, lookback, and missing-value propagation for every indicator.

P1 — Input/output contract

High risk

The source is a multi-row yfinance CSV, while the target JSON and CSV schemas are only partially defined. Timestamp handling, serialization, field order, and naming conventions need clarification.

Proposed resolution: define a normalized internal schema and explicit serialization rules for both output formats.

#### Specific shape-rule concerns

1\. The neutral flat-candle rule may override a doji. The document defines a neutral doji when `C = O`, followed by a flat neutral candle when `H = L`. A candle with all four OHLC values equal satisfies both conditions.

Recommended precedence:

1. If `H = L`, classify as `flat_neutral_candle`.
2. Otherwise, if `C = O`, classify as `doji_neutral_candle`.
3. Otherwise, classify as bullish or bearish based on `C` versus `O`.

This is a proposed convention, not a rule already established by the specification.

2\. Some bullish and bearish shapes can match more than one rule. For example, a bullish candle with a body ratio of 0.30, upper-wick ratio of 0.20, and lower-wick ratio of 0.50 may satisfy both the spinning-top and hammer criteria, depending on the absolute wick/body condition. Because spinning top appears first, it wins.

Recommended resolution: either retain this order as a formal requirement or adjust the criteria to remove unintended overlaps. Test every rule at its exact threshold.

3\. Wick proportions should have an invariant. For valid OHLC data and nonzero range, the three ratios should sum to approximately 1:

\\[ \text{BodyRatio}+\text{UpperWickRatio}+\text{LowerWickRatio}=1 \\]

Use this as a validation test. It helps detect calculation errors in either the bullish or bearish branches.

### C. ATR and volatility magnitude

| -- | -------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| C1 | ATR(9) is described as the mean of the first nine true ranges followed by Wilder smoothing, but the precise first true range is not fully defined. | Define the first TR as `H − L`, unless a previous close exists and the chosen convention specifies otherwise. |
| C2 | The formula refers to `ATR(t−1)`, but its missing-value behavior is not defined.                                                                   | Keep `BodyATR` and `RangeATR` null until the previous row's ATR is valid and positive.                        |
| C3 | The warm-up note refers generally to periods 1–8, but the first valid ATR depends on whether the first row's TR counts as observation 1.           | Define zero-based row indexes and exact first-valid positions.                                                |
| C4 | The magnitude thresholds start at `rangeATR >= 2.0`, then 1.5, 1.0, and 0.5.                                                                       | Document the interval boundaries and the null-ATR case.                                                       |
| C5 | The heading spells `magnitud` while the subsequent assignment and JSON use `magnitude`.                                                            | Standardize the name as `magnitude`.                                                                          |

The ATR worked example is arithmetically consistent: the three listed true ranges are 5, 6, and 4, giving ATR(3) = 5. The remaining issue is alignment and initialization, not that example's arithmetic.

Recommended magnitude classification contract:

| Condition                        | Output                |
| -------------------------------- | --------------------- |
| `range_atr >= 2.0`               | `monster_move`        |
| `1.5 <= range_atr < 2.0`         | `exceptionally_large` |
| `1.0 <= range_atr < 1.5`         | `large`               |
| `0.5 <= range_atr < 1.0`         | `normal`              |
| `range_atr < 0.5`                | `small`               |
| `range_atr` is null or undefined | null                  |

This makes the intended boundaries explicit and avoids assigning a magnitude to an uncomputable value.

### D. RVOL and missing volume

| ID | Issue                                                                                                                                               | Proposed resolution                                                                                                                                                               |
| -- | --------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D1 | RVOL is described as current volume divided by average volume over N periods, but it is unclear whether the current bar is included in the average. | Specify that the baseline uses the N preceding bars only, excluding the current bar, if the intention is to compare current activity against historical activity.                 |
| D2 | The example says “9 past periods + current period,” but the implementation requirements do not formally state the baseline window alignment.        | Define `rvol[t] = volume[t] / mean(volume[t−N:t])`, using a clearly documented indexing convention.                                                                               |
| D3 | Zero or missing baseline volume is assigned `0.0`.                                                                                                  | Distinguish missing baseline, zero baseline, zero current volume, and valid positive baseline. Do not use one value to represent all cases without an explicit business decision. |
| D4 | “Standard Daily RVOL” is the heading, but the pipeline also supports intraday intervals.                                                            | Clarify whether the same-period RVOL formula applies to all intervals or whether intraday RVOL needs time-of-day normalization.                                                   |
| D5 | Negative, nonnumeric, or missing volume values have no defined handling.                                                                            | Reject invalid volume values or mark the relevant features invalid according to a documented policy.                                                                              |

My recommendation for RVOL: Use the previous N observations as the baseline and return null when the baseline is unavailable or invalid. Return `0.0` only when the current volume is genuinely zero and the baseline is positive. If backward compatibility requires `0.0` for an invalid baseline, document that as a deliberate sentinel convention.

This avoids conflating “no relative activity” with “relative activity could not be calculated.”

A particularly important distinction is the difference between warm-up and invalid data. Warm-up means insufficient history; invalid data means the calculation's input is missing or unusable. They should not automatically share the same recovery behavior.

For slope, I recommend:

\\[ \text{Slope}\_N(t)= \frac{MA_N(t)-MA_N(t-9)}{MA_N(t-9)}\times100 \\]

where \\(MA_N\\) is the specified EMA or SMA. Return null when either moving-average value is unavailable or the earlier value is zero.

Also clarify whether all slopes are expressed as percentages on a 0–100 scale or ratios on a 0–1 scale. The formula currently specifies percentages.

### F. Predecessor-bar relationships — a structural inconsistency

This section needs more than editorial cleanup.

The specification defines three possible high relationships (`HH`, `LH`, `EH`) and three low relationships (`HL`, `LL`, `EL`). Their Cartesian product contains exactly nine combinations, not twelve. The document's “12 unique” list includes combinations that cannot arise under its own comparison rules, such as `HH-EL` being valid but `EL-LH` requiring a different ordering convention from the listed high-low pairing.

The actual nine combinations under the defined algorithm are:

| High relation | Low relation | Code    |
| ------------- | ------------ | ------- |
| Higher high   | Higher low   | `HH-HL` |
| Higher high   | Lower low    | `HH-LL` |
| Higher high   | Equal low    | `HH-EL` |
| Lower high    | Higher low   | `LH-HL` |
| Lower high    | Lower low    | `LH-LL` |
| Lower high    | Equal low    | `LH-EL` |
| Equal high    | Higher low   | `EH-HL` |
| Equal high    | Lower low    | `EH-LL` |
| Equal high    | Equal low    | `EH-EL` |

The existing code table has a particularly consequential error: `LH-HL` is called an “Inside Bar.” Under the supplied definitions, an inside bar requires the current high to be below the previous high and the current low to be above the previous low, so `LH-HL` is correct for that specific definition. However, it should be categorized consistently with the other contraction patterns.

The document also lists `EL-LH`, `EL-HH`, and `EL-EH`, which appear to reverse the order of the relation codes in the stated `highRelation + "-" + lowRelation` concatenation. That means the listed 12-pattern taxonomy cannot be implemented as written.

Recommended resolution:

1. Choose one canonical code format: `highRelation-lowRelation`.
2. Enumerate the nine possible combinations from the algorithm.
3. Assign exactly one name and category to each code.
4. Remove the three reversed codes unless they represent a separate, explicitly defined concept.
5. Add tests for all nine combinations, including equality cases.

One more issue: the names “Bullish Fakeout,” “Bearish Fakeout,” and “Perfect Double Top/Bottom” imply market interpretation that cannot be established from two bars' high/low comparisons alone. Either rename these as structural descriptions or document the additional criteria needed to justify those interpretations.

The output example also has values such as `rvol: 999999999` and placeholder moving-average values. These are illustrative, but the document should explicitly label them as placeholders so test fixtures do not accidentally validate against them.

Recommended serialization rules:

- JSON: one object per observation, with stable field names and numeric values; use `null` for unavailable calculations.
- CSV: one row per observation, with the same logical fields and a stable column order.
- Preserve full computational precision internally; round only when explicitly required for presentation or export.
- Keep timestamps and ticker identity consistent between both formats.
- Ensure both outputs contain the same observations in the same chronological order.

## 3. Additional gaps that should be resolved

These are requirements that are not fully defined in the current document, rather than necessarily incorrect formulas.

### Gaps in operational behavior

G1. Data gaps and missing observations

What happens if a trading session or intraday bar is missing? The predecessor relationship should normally compare consecutive available observations, not assume that adjacent rows are adjacent trading periods. Indicators may also behave differently if gaps are silently ignored.

Recommendation: Preserve timestamps, calculate on the available observations by default, and optionally flag gaps. Do not synthesize missing bars unless explicitly configured.

G2. Mixed intervals and session boundaries

Daily and intraday data have different semantics. Intraday data may cross trading sessions, and the first bar of a session may need special treatment for volume and previous-close calculations.

Recommendation: Identify the bar interval and trading-session policy in the processing configuration. Explicitly decide whether indicators roll continuously across sessions or reset.

G3. Corporate actions and adjusted prices

The example shows price fields but does not state whether the data uses adjusted or unadjusted prices. Corporate-action adjustments can affect indicator continuity, true range, and comparisons.

Recommendation: Document the source adjustment policy and require consistent price treatment throughout a series.

G4. Reproducibility and validation

There is no complete test suite specification, versioning policy, or reference output against which implementations can be compared.

Recommendation: Add small deterministic fixtures with expected values for each feature, and test daily and intraday input separately.

## 4. Recommended calculation contract

I would add a shared section near the beginning of the README so all feature definitions follow the same rules.

## Calculation and Data Handling Contract

### 1. Input validation

- Input data must contain valid timestamps and the required OHLCV fields.
- Rows must be processed in chronological order.
- Missing values, duplicate timestamps, and invalid numeric values must follow an explicitly configured validation policy.
- OHLC values must not be silently corrected or normalized.

### 2. Numeric conventions

- Use unrounded values for all intermediate calculations and threshold comparisons.
- Define one consistent output precision policy.
- All ratios and percentages must have documented units.
- Division by zero must never cause an unhandled runtime exception.

### 3. Missing values and warm-up

- Insufficient historical data produces null calculated values.
- Invalid or missing inputs must be distinguished from normal warm-up.
- A calculation must be null when its required inputs are unavailable or its denominator is invalid.
- JSON nulls and CSV empty cells must represent unavailable calculations consistently.

### 4. Indicator initialization

- Every indicator must define its formula, initialization method, lookback, first valid observation, and missing-data behavior.
- Rolling windows must specify whether the current observation is included.
- Historical comparisons must define their exact row offsets.

### 5. Classification

- Every valid candle must receive exactly one direction and one shape classification, subject to explicitly defined neutral and invalid-data cases.
- Classification rules must have deterministic precedence or mutually exclusive conditions.
- Every predecessor-bar combination must map to exactly one code, name, and category.

### 6. Output consistency

- JSON and CSV must contain the same observations and logical calculated fields.
- A canonical ordered schema must define field names, types, and output order.
- Timestamps must be serialized consistently and retain their intended timezone semantics.
- Calculated field names must use one documented naming convention.

### 7. Testing

- Each formula must have at least one deterministic test.
- Threshold boundaries, warm-up periods, zero denominators, missing values, and degenerate candles must be tested.
- Both output formats must be validated against the same expected results.

## 6. Decisions I recommend confirming

Before treating the specification as implementation-ready, I would prioritize these five decisions:

1. RVOL: Should the average use only the previous nine bars, excluding the current bar? I recommend yes.
2. Invalid baseline: Should missing or zero baseline volume return null, or must it return `0.0` for backward compatibility? I recommend null.
3. EMA initialization: Should all EMA periods use the SMA of the first N closes as their seed? This is a reasonable deterministic default, but should be consistent with the existing EMA9 specification.
4. Neutral candles: When `H = L` and `C = O`, should `flat_neutral_candle` take precedence over `doji_neutral_candle`? I recommend the flat classification.
5. Predecessor taxonomy: Should the system use exactly the nine combinations generated by the current high/low comparison algorithm, or is there a separate reason for the 12 entries in the prose list? I recommend the nine combinations unless the intended taxonomy is expanded and formally defined.

## Final assessment

The README is a good working draft, but not yet a fully deterministic implementation specification. Most of the problems can be resolved without changing the overall purpose or introducing new indicators.

The most important next step is to settle the calculation contract and classification tables first. Otherwise, two developers could follow the document faithfully and still produce different output for the same source file.

I would keep the established formulas where they are clear, document intentional exceptions such as SMA-based `slope20`, and make every remaining design choice explicit rather than silently changing the intended behavior.
