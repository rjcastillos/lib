# Review of the ATR specification: issues, decisions, and recommended resolutions

The four points are valid and should be resolved explicitly in the ATR specification before implementation is considered complete. I would also clarify one important distinction: a missing or invalid bar is a data-quality event, not necessarily a reason to reset ATR permanently. The correct recovery behavior depends on the policy chosen for the indicator.

The recommendations below distinguish the existing specification and implementation behavior from the proposed contract.

## 1. Missing-data recovery — blocker

### What needs clarification

ATR depends on True Range (TR), and TR depends on the current bar's high and low plus the previous bar's close:

\\[ TR_t=\max\left(H_t-L_t,\ |H_t-C\_{t-1}|,\ |L_t-C\_{t-1}|\right) \\]

If the current bar is invalid, its TR cannot be calculated reliably. If its close is missing, the next bar's TR may also be unavailable because it needs that close. The specification must define how ATR recovers after this happens.

### Recommended resolution: restart the valid-TR seed sequence

I recommend a consecutive-valid-observations policy:

1. An invalid bar receives `TR = null` and `ATR = null`.
2. If the current bar's OHLC or the previous close needed for TR is unavailable, its TR is null.
3. After a TR is null, do not continue smoothing from the last ATR as if no observation were missing.
4. Start collecting a new sequence of consecutive valid TR values.
5. Once `N` consecutive valid TR values have been collected, seed ATR with their arithmetic mean.
6. Continue with Wilder's smoothing:

\\[ ATR_t=\frac{(N-1)ATR\_{t-1}+TR_t}{N} \\]

This policy is conservative, easy to test, and prevents an ATR value from silently bridging a data gap.

An alternative is to resume smoothing from the last valid ATR as soon as a valid TR appears. That retains more data but treats the gap as if the historical volatility state were still reliable. Either policy can be implemented, but it must not be left implicit. I recommend the restart policy for this specification.

## 2. Price validation — blocker

The main pipeline README says OHLC validation should be minimal, but its predecessor section later specifies finite prices and structural consistency. The ATR specification and implementation should use the same validation contract.&#x20;

### Recommended resolution

For the whole OHLCV pipeline, require:

- All required OHLC values are numeric and finite.
- `Open > 0`, `High > 0`, `Low > 0`, and `Close > 0`.
- `High >= Low`.
- `High >= max(Open, Close)`.
- `Low <= min(Open, Close)`.
- Volume is finite and non-negative when present, with missing-volume handling defined separately.

I recommend positive prices for this project because other pipeline calculations normalize price movement by the open price, such as `BodyPercent = Body / Open`. Allowing a zero or negative open would make that calculation undefined or misleading.

Should Close be constrained to the High–Low range? Yes. For valid OHLC bars, the high must be at least as high as the open and close, and the low must be at most as low as the open and close. Reject invalid bars or return a documented invalid-row result; do not silently repair prices.

One nuance: ATR's mathematical formula itself can work with negative prices, as it uses price differences. Positive-price validation is therefore a project-wide data-domain choice, not a mathematical requirement of ATR. If the pipeline is later intended to support instruments that can trade at zero or negative prices, that domain policy should be revisited alongside every formula that divides by the open price.

## 3. Period contract — blocker

The main pipeline README specifies ATR(9), while you note that the current `calculate_atr` implementation defaults to 14. These defaults conflict and must be reconciled.&#x20;

### Recommended resolution

Use the following contract:

- `period` must be an integer greater than or equal to 1.
- The project pipeline default is 9, to match the existing ATR(9) specification.
- An explicitly supplied valid period overrides the default.
- Reject zero, negative values, non-integer values, and booleans.
- The initial ATR requires `period` consecutive valid TR observations.
- The first ATR is seeded with the arithmetic mean of those `period` TR values.

If the reusable function is intended to follow a conventional default of 14, make the period mandatory at the pipeline call site instead of allowing a hidden default to override ATR(9). My preference is a default of 9 for this project because it avoids inconsistent results when the caller omits the argument.

## 4. Input ordering and output representation — design details

### Input ordering

Specify that input bars:

1. Belong to one instrument and one timeframe per calculation.
2. Are ordered chronologically in ascending timestamp order.
3. Have at most one bar per timestamp.
4. Use the previous bar in that ordered series for the previous close in TR calculations.

The implementation should either reject out-of-order or duplicate timestamps with a clear error, or explicitly normalize them before calculation. I recommend validating the input order and rejecting duplicates rather than silently sorting, because sorting or deduplication can conceal upstream data problems.

A gap in timestamps does not automatically mean the bar is invalid. If a valid bar follows an overnight, weekend, or other interval gap, its TR should still account for the previous available close, unless the specification explicitly defines a session-reset policy.

### `null` versus Python `NaN`

These are different representations of an unavailable value:

- Python/pandas calculation layer: use `NaN` for unavailable numeric results if that is what the implementation already returns.
- JSON output: convert unavailable numeric values to JSON `null`. Standard JSON does not support `NaN`.
- CSV output: represent unavailable numeric values as an empty field by default, and document this convention. If downstream consumers require a literal `NULL`, specify that instead.

Do not allow `NaN` to leak into JSON as the non-standard token `NaN`. Apply the conversion at the serialization boundary so the calculation layer can retain its existing numeric representation.

## 5. Proposed normative pseudocode

The following pseudocode combines the recommended validation, missing-data recovery, and period rules.

```

FUNCTION calculateATR(bars, period = 9):

    REQUIRE period is an integer >= 1
    REQUIRE bars are chronological and belong to one series

    previousClose = NULL
    consecutiveValidTRs = empty list
    previousATR = NULL

    FOR each bar in bars:

        IF bar has invalid or missing OHLC:
            bar.TR = NULL
            bar.ATR = NULL

            previousClose = NULL
            consecutiveValidTRs = empty list
            previousATR = NULL
            CONTINUE

        IF bar.High < max(bar.Open, bar.Close) OR
           bar.Low > min(bar.Open, bar.Close) OR
           bar.High < bar.Low:
            bar.TR = NULL
            bar.ATR = NULL

            previousClose = NULL
            consecutiveValidTRs = empty list
            previousATR = NULL
            CONTINUE

        IF previousClose is NULL:
            # First valid bar after the start or a data gap
            bar.TR = bar.High - bar.Low
        ELSE:
            bar.TR = max(
                bar.High - bar.Low,
                abs(bar.High - previousClose),
                abs(bar.Low - previousClose)
            )

        APPEND bar.TR to consecutiveValidTRs

        IF previousATR is NULL:
            IF length(consecutiveValidTRs) < period:
                bar.ATR = NULL
            ELSE:
                bar.ATR = MEAN(last period TR values)
                previousATR = bar.ATR
        ELSE:
            bar.ATR = (
                (period - 1) * previousATR + bar.TR
            ) / period

            previousATR = bar.ATR

        previousClose = bar.Close

    RETURN bars with TR and ATR
END FUNCTION

```

Important refinement to the pseudocode: When a valid OHLC bar follows an invalid bar, it can still calculate its own `TR = High - Low`, even though the previous close is unavailable. That is the conventional first-bar True Range calculation and permits recovery without using a stale close. The implementation must consistently treat that bar as the beginning of a new valid TR sequence.

This means recovery works as follows:

- An invalid bar produces null TR and ATR.
- The next valid bar uses its own high minus low as TR and starts the new sequence.
- ATR remains null until `period` consecutive valid TR values have accumulated.
- Once seeded, Wilder smoothing resumes.

The pseudocode's reset behavior should therefore be implemented so that a valid bar after a gap starts a new sequence rather than being skipped. In production, also ensure a missing or invalid close cannot be reused as `previousClose`.

## Final recommendation

Adopt the restart-after-invalid-data policy, use positive and structurally consistent OHLC prices for the current pipeline, and set the project ATR default to 9. Explicitly define chronological input and convert Python `NaN` values to JSON `null` during serialization.

One final implementation detail worth recording: the first bar of an entire series has no previous close, but its TR is still `High - Low`. That same rule should apply to the first valid bar after a gap. It avoids an unnecessary extra warm-up observation and gives the recovery behavior a clear, testable definition.
