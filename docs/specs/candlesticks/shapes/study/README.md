## 7. Candle-shape rules
- Shape
- Direction


### 7.1 Candles shape and direction classification principles

1. Direction is independent of shape. `direction` is `bullish` when `C > O`, `bearish` when `C < O`, and `neutral` when `C = O`.
2. Neutral candles are handled first. A candle with `H = L` is classified as flat; otherwise, a candle with `C = O` is classified as a doji.
3. Shapes are based on normalized body and wick proportions. The thresholds are the same for bullish and bearish candles.
4. Rules must be mutually exclusive. Each rule uses a distinct region of the proportion space, with explicit precedence only for defensive handling.
5. Unclassified shapes are avoided for valid candles. The final fallback is a general shape such as `standard`, not a direction-specific unclassified shape.
6. Zero-body candles are excluded from bullish/bearish shape rules. This avoids the problem of a zero body satisfying comparisons such as `wick >= 2 × body`.


### 7.2 Canonical geometry formulas

Replace the separate bullish and bearish proportion formulas with a single shared definition.

```
Range     = H - L
Body      = abs(C - O)
UpperWick = H - max(O, C)
LowerWick = min(O, C) - L

BodyPercent      = Body / Range
UpperWickPercent = UpperWick / Range
LowerWickPercent = LowerWick / Range
```

These formulas are symmetric for bullish and bearish candles. They also eliminate the need to maintain two copies of the same calculations.

For `Range = 0`, do not calculate the ratios. Classify the candle as `flat_neutral_candle` when `C = O`; otherwise, return `flat_bullish_candle` or `flat_bearish_candle` if such inputs are permitted. Under valid OHLC data, a zero-range candle necessarily has `C = O`.

### 7.3 Candle model

Every input row represents one candle. Calculate its own direction and shape, and then compare its high and low with those of the preceding candle.

| Dimension                   | Uses                       | Answers                                      |
| --------------------------- | -------------------------- | -------------------------------------------- |
| `direction`                 | Current O and C            | Was the candle bullish, bearish, or neutral? |
| `shape`                     | Current O, H, L, C         | What is the candle’s geometry?               |
| `predecessor.high_relation` | Current H vs previous H    | Did the high rise, fall, or stay equal?      |
| `predecessor.low_relation`  | Current L vs previous L    | Did the low rise, fall, or stay equal?       |
| `predecessor.pattern_code`  | Both predecessor relations | Which of the nine combinations occurred?     |

Important: shape and predecessor relationship are independent classifications. The shape algorithm must not use the previous candle, and the predecessor algorithm must not use the candle’s shape or direction.

For example, `bullish_hammer_shape` and `HH-LL` are not contradictory. The first describes the candle's body and wicks; the second says the candle's high exceeded the previous high while its low fell below the previous low.

### 7.4 Candle shape: canonical thresholds and precedence

Apply these fixed thresholds to valid candles using unrounded ratios. `BodyRatio`, `UpperWickRatio`, and `LowerWickRatio` are defined in section 7.2. The same thresholds apply to bullish and bearish candles; only the directional mapping of the rejection and long wicks changes.

| Precedence | Shape | Body ratio | Wick requirements |
| --- | --- | --- | --- |
| 1 | `flat_neutral_candle` | Range is zero | Valid OHLC implies `C = O`. |
| 2 | `doji_neutral_candle` | `C = O`, nonzero range | No additional wick requirement. |
| 3 | `bullish_marubozu` / `bearish_marubozu` | `>= 0.90` | Both wick ratios `<= 0.05`. |
| 4 | `bullish_lower_rejection` / `bearish_upper_rejection` | `>= 0.60` and `< 0.90` | Rejection-side wick ratio `>= 0.15`; opposite wick ratio `<= 0.10`. |
| 5 | `bullish_momentum` / `bearish_momentum` | `>= 0.60` and `< 0.90` | Both wick ratios `<= 0.20`, excluding candles matching rejection. |
| 6 | `bullish_hammer_shape` / `bearish_hammer_shape` | `> 0` and `<= 0.35` | Long wick ratio `>= 0.50`; opposite wick ratio `<= 0.10`; long wick size `>= 2 * Body`. |
| 7 | `bullish_inverted_hammer_shape` / `bearish_inverted_hammer_shape` | `> 0` and `<= 0.35` | Mirrored hammer rule: upper long wick for bullish, lower long wick for bearish. |
| 8 | `bullish_spinning_top` / `bearish_spinning_top` | `> 0` and `<= 0.30` | Both wick ratios `>= 0.20`. |
| 9 | `bullish_standard` / `bearish_standard` | Any remaining valid directional candle | Fallback; no additional restriction. |

For rejection and hammer rules, the rejection/hammer long wick is the lower wick for bullish candles and the upper wick for bearish candles. For inverted-hammer rules, those directions are reversed. Neutral rules are evaluated before directional rules. Rejection takes precedence over momentum; the remaining ratio bands and wick constraints make the other specialized classifications mutually exclusive. Every valid non-neutral candle must receive exactly one directional shape.

## 7.5 Predecessor relationship:

The code is always `high_relation-low_relation`, so there are exactly nine combinations.

| Pattern code | `pattern_name`           | What changed?              |
| ------------ | ------------------------ | -------------------------- |
| `HH-HL`      | `upward_shift`           | Higher high, higher low    |
| `HH-EL`      | `upper_expansion`        | Higher high, unchanged low |
| `HH-LL`      | `outside_bar`            | Higher high, lower low     |
| `LH-HL`      | `inside_bar`             | Lower high, higher low     |
| `LH-LL`      | `downward_shift`         | Lower high, lower low      |
| `LH-EL`      | `upper_contraction`      | Lower high, unchanged low  |
| `EH-HL`      | `lower_contraction`      | Unchanged high, higher low |
| `EH-LL`      | `lower_expansion`        | Unchanged high, lower low  |
| `EH-EL`      | `unchanged_boundaries`   | Both extremes unchanged    |

The approved names describe only the relationship geometry, not a bullish or bearish market signal. `outside_bar` and `inside_bar` are conventional concise names. The other names describe shifts or changes in the upper (high) and lower (low) boundaries. For example, an outside bar can be bullish or bearish depending on its open and close. These labels are the finalized `pattern_name` output values.

### 7.5.1 comparison rules

To make the implementation deterministic, we have specified the following rules.

A. Equality and price precision

Floating-point prices can make two theoretically equal values appear slightly different. Use a documented equality policy:

- Prefer comparing prices normalized to the instrument’s valid tick size, when that information is available.
- Otherwise, use exact equality on the normalized input prices and document that choice.
- Do not silently introduce an arbitrary tolerance.

The three comparisons must be mutually exclusive: every valid comparison produces exactly one relation.

B. First candle

The first candle has no predecessor. Its shape and direction are still calculated. Its four relationship fields (`high_relation`, `low_relation`, `pattern_code`, and `pattern_name`) must be `null`, and its predecessor `status` must be `NO_PREDECESSOR`.

C. Missing predecessor

If the immediately preceding row has invalid or missing high/low values, the relationship is unavailable. Do not skip that row and compare with an older candle unless a separate gap-recovery rule explicitly permits it.

D. OHLC validation

Require finite, positive numeric OHLC values and the structural constraints:

\\[ H \geq \max(O,C), \qquad L \leq \min(O,C), \qquad H \geq L \\]

An invalid candle must produce a candle-specific error in this format, using the timestamp as represented in the feed:

```text
Ticker <Ticker> has an invalid candle at <timestamp> (in the feed). Please check.
```

For an invalid supplied Volume value, report:

```text
Ticker <Ticker> has invalid volume at <timestamp> (in the feed). Please check.
```

For a daily candle without a time, use its feed date as `<timestamp>`. Write each validation error to standard error, continue with the next row, and write a final summary to standard error with the number of valid and invalid rows and whether both output files were written. Count a row only once as invalid even if it has more than one validation error. If both output files are written but one or more rows are invalid, the command exits with status `1`. It exits with status `0` only when both output files are written and all rows are valid. A fatal input, processing, or output failure that prevents completing both outputs exits with status `2`.

Retain the input row in both outputs. Preserve finite numeric source values even when a candle violates structural OHLC rules, but do not assign that candle a direction, shape, candle geometry, or predecessor classification. Represent missing, non-numeric, NaN, or infinite numeric inputs as JSON `null` and an empty CSV cell. Missing Volume is allowed and is not an error. For supplied invalid Volume, preserve valid OHLC-based candle and predecessor calculations while making `volume` and affected `rvol` results unavailable. The immediately following row must not skip an invalid OHLC candle to find an older predecessor; its predecessor fields are unavailable. Other indicators follow their own input-validity and warm-up rules.

E. Session and timeframe boundaries

Use the immediately preceding row in the chronologically sorted series for the same ticker and timeframe. Do not compare different tickers or timeframes, and do not skip an invalid preceding row. Comparisons may cross overnight, weekend, or other session gaps; compare consecutive available rows in the series.

F. 3 fields to define a candle 
We use `direction` + `shape` + `predecessor pattern code` as three separate output fields. This makes the design coherent, eliminates the predecessor-code inconsistency, and prevents future shape changes from breaking predecessor analysis. The nine predecessor codes form a complete classification of high/low relationships; descriptive trading interpretations should remain a separate, optional layer with their own explicit criteria.

### 7.5.2 predecessor pseudocode 


FUNCTION classifyPredecessorRelationship(previousCandle, currentCandle):

    # STEP 1 — Check that a predecessor exists
    IF previousCandle does not exist:
        RETURN {
            highRelation: NULL,
            lowRelation: NULL,
            patternCode: NULL,
            patternName: NULL,
            status: "NO_PREDECESSOR"
        }

    # STEP 2 — Validate required prices
    IF previousCandle.High is missing OR
       previousCandle.Low is missing OR
       currentCandle.High is missing OR
       currentCandle.Low is missing:

        RETURN {
            highRelation: NULL,
            lowRelation: NULL,
            patternCode: NULL,
            patternName: NULL,
            status: "MISSING_PRICE"
        }

    IF any required price is non-numeric OR non-finite:
        RETURN {
            highRelation: NULL,
            lowRelation: NULL,
            patternCode: NULL,
            patternName: NULL,
            status: "INVALID_PRICE"
        }

    # STEP 3 — Validate high/low boundaries
    IF previousCandle.High < previousCandle.Low OR
       currentCandle.High < currentCandle.Low:

        RETURN {
            highRelation: NULL,
            lowRelation: NULL,
            patternCode: NULL,
            patternName: NULL,
            status: "INVALID_OHLC"
        }

    # STEP 4 — Normalize prices for comparison
    # Use the instrument's tick-size policy, if available.
    prevHigh = normalizePrice(previousCandle.High)
    prevLow  = normalizePrice(previousCandle.Low)
    currHigh = normalizePrice(currentCandle.High)
    currLow  = normalizePrice(currentCandle.Low)

    # STEP 5 — Classify the high relationship
    IF currHigh > prevHigh:
        highRelation = "HH"
    ELSE IF currHigh < prevHigh:
        highRelation = "LH"
    ELSE:
        highRelation = "EH"

    # STEP 6 — Classify the low relationship
    IF currLow > prevLow:
        lowRelation = "HL"
    ELSE IF currLow < prevLow:
        lowRelation = "LL"
    ELSE:
        lowRelation = "EL"

    # STEP 7 — Build the canonical pattern code
    patternCode = highRelation + "-" + lowRelation

    # STEP 8 — Map code to a descriptive name
    patternName = PATTERN_NAME_MAP[patternCode]

    # STEP 9 — Return the result
    RETURN {
        highRelation: highRelation,
        lowRelation: lowRelation,
        patternCode: patternCode,
        patternName: patternName,
        status: "OK"
    }
END FUNCTION

PATTERN_NAME_MAP = {
    "HH-HL": "upward_shift",
    "HH-EL": "upper_expansion",
    "HH-LL": "outside_bar",
    "LH-HL": "inside_bar",
    "LH-LL": "downward_shift",
    "LH-EL": "upper_contraction",
    "EH-HL": "lower_contraction",
    "EH-LL": "lower_expansion",
    "EH-EL": "unchanged_boundaries"
}

# 17 RVOL
## Prior-bars relative volume

For each candle, calculate RVOL as its volume divided by the arithmetic mean of the volumes of the immediately preceding 9 bars in the same ticker and timeframe:

```text
RVOL[t] = Volume[t] / mean(Volume[t-9], ..., Volume[t-1])
```

The current bar is excluded from the baseline. Daily input therefore compares with the previous 9 daily bars; intraday input compares with the previous 9 bars at that intraday timeframe. This is a prior-bars calculation, not an intraday time-of-day-adjusted RVOL calculation.

Return `null` when fewer than 9 previous bars exist, the current volume or any of the 9 baseline volumes is missing or invalid, or the baseline average is zero. Do not skip a missing/invalid volume to reach an older bar. Missing volume is allowed: serialize it as unavailable and do not report an error solely because it is absent. A supplied negative, non-numeric, NaN, or infinite volume is invalid: report it using the volume-specific validation error in section D, serialize it as unavailable, and do not use it in RVOL. Invalid volume does not invalidate candle calculations that have valid OHLC. Return `0.0` when the current volume is genuinely zero and the baseline average is positive. RVOL is a ratio and is not multiplied by 100.

Example: previous-bar volumes are `12,000, 15,000, 11,000, 14,000, 16,000, 13,000, 15,000, 17,000, 14,000`; current volume is `28,000`.

```text
Baseline average = 127,000 / 9
RVOL = 28,000 / (127,000 / 9) = 252,000 / 127,000
     = 1.984251968503937
```

## 27. Slope calculation rules and interpretation

### 27.1 General calculation and validity rules

All four slope indicators use the same calculation principle. In this study, the raw slope output is a decimal fraction: for example, `0.04` represents `4%`. Do not multiply the stored/exported slope by 100. Multiply by 100 only when converting it to a human-readable percentage for interpretation.

1. Calculate the relevant moving average according to its own specification.
2. Compare its current value with its value exactly 9 observations earlier.
3. Calculate the fractional change using the historical value as the denominator.
4. Return `null` until both required moving-average values are available.
5. Return `null` if the historical denominator is zero or invalid.

The first valid slope bar is therefore determined by:

```

FirstValidBar = MovingAveragePeriod + 9 

```


This assumes:

- One-based bar numbering.
- Continuous, uninterrupted input data.
- The moving average first becomes valid at its own period number.
- No missing or invalid observations interrupt the calculation.

First valid output summary:

| Indicator | Moving average | MA first valid bar | Slope lag | First valid slope bar |
| --------- | -------------- | ------------------ | --------- | --------------------- |
| SLOPE9    | EMA9           | 9                  | 9         | 18                    |
| SLOPE20   | SMA20          | 20                 | 9         | 29                    |
| SLOPE50   | EMA50          | 50                 | 9         | 59                    |
| SLOPE200  | EMA200         | 200                | 9         | 209                   |

If missing or invalid data interrupts the moving-average calculation, the slope must remain `null` until both the current and historical moving-average values are valid again.

### 27.2 Slope interpretation

For better understanding before interpreting the slopes convert the values from its decimal forms to percentages for example 0.04 * 100 = 4%.

The following thresholds provide a descriptive interpretation of the calculated slope. They do not alter the underlying calculation.

| Slope percentage                               | Interpretation      |
| ---------------------------------------------- | ------------------- |
| Greater than +4%                               | `strong_bull_trend` |
| Greater than +2% and up to +4%                 | `bull_trend`        |
| Greater than or equal to -2% and up to +2%     | `sideways`          |
| Greater than or equal to -4% and less than -2% | `bear_trend`        |
| Less than -4%                                  | `strong_bear_trend` |

Boundary values are assigned to only one category:

- Exactly `+4%` is `bull_trend`.
- Exactly `+2%` is `bull_trend`.
- Exactly `-2%` is `sideways`.
- Exactly `-4%` is `bear_trend`.

The interpretation should only be assigned when the corresponding slope value is not `null`.

Important implementation note: The slope lookback is always 9 observations. It is not the moving-average period. For example, SLOPE200 compares EMA200 at the current bar with EMA200 nine bars earlier; it does not compare it with EMA200 two hundred bars earlier.
